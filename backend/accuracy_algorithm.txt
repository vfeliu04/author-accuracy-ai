Accuracy Verification Pipeline
==============================

This note mirrors the current Python implementation under `backend/author_ai/pipelines`.


Source indexing
---------------
1. **Reset & ingest** – `/api/run_pipeline` calls `reset_environment()` and instantiates `AccuracyPipeline`. Each SOURCE upload is ingested via `IngestionPipeline.ingest`.
2. **OCR & parsing** – `ingest` runs OCRmyPDF only when heuristics flag a scanned PDF. PyPDF2 extracts per-page text plus tables (Tabula / pdf_tables helper).
3. **Recursive/semantic chunking** – Each page’s text is split with LangChain’s `RecursiveCharacterTextSplitter` (1 200 char chunks, 200 overlap, separators `["\n\n","\n",". "," ",""]`). Every chunk stores metadata:
   - `parent_id = page-{n}`
   - `parent_title = "Page n"`
   - `parent_page = n`
4. **Section summaries (LlamaIndex)** – For each page/section, we invoke LlamaIndex’s `SummaryIndex` (powered by the configured OpenAI model) to produce a concise synopsis. This is stored in `sections_detail`. If LlamaIndex isn’t available, we fall back to the heuristic summarizer. When `SECTION_SUMMARY_MODE=lazy` (default), section summaries are skipped at ingestion and generated on-demand only when a claim/evidence needs that section; the first generated summary is cached in `sections_detail`.
5. **Persistence** – Chunks are inserted into SQLite (`chunks` table) and the document metadata records `sections_detail` (including LlamaIndex summaries) so we can recover the full parent text later. The chunk list is embedded via `embed_texts` (OpenAI `text-embedding-3-large`) and stored in FAISS with matching metadata (`chunk_id`, `doc_id`, snippet, parent info). The FAISS index is wrapped by LangChain’s `FAISS` vector store so we can call `similarity_search` later.


Report verification
-------------------
1. **Claim extraction (light classifier)** – `AccuracyPipeline.verify_report` ingests the REPORT PDF, splits sentences, strips list markers, and passes each numeric sentence through a lightweight, dependency-free classifier:
   - Features: has digit, has unit/year token, verb hint, token length, alpha ratio, trailing-number heuristic, title/colon heuristic.
   - Score: +2 (digit), +2 (unit/year), +1 (verb), +0.5 (≥4 tokens), −2 (very low alpha ratio), −1.5 (lone trailing number without unit), −1 (colon/title without unit).
   - Threshold: keep as claim if score ≥ 1.5. This filters headers/bullet numbers while retaining real numeric statements. Claims also carry parent section/page IDs and the `sections_detail` summary for context.
2. **Evidence retrieval** – `_retrieve_evidence`:
   - Calls `VectorStore.similarity_search(claim_text, k=5)` to fetch snippets plus metadata and reconstructs parent sections (page text + LlamaIndex summary) using `sections_detail` cached from SQLite.
   - LLM rerank: pass the similarity-ordered hits to `EvidenceReranker` (OpenAI Chat Completion using `RERANK_MODEL`, default `gpt-4o-mini`), which emits `index|score` output and final ordering. If the API key or library is unavailable, the step gracefully skips.
   - Verdict classification:
     * If the FAISS similarity score `s_max` exceeds `RETRIEVAL_SUPPORT_THRESHOLD`, call `VerdictClassifier` (OpenAI chat JSON response or heuristic numeric comparison) to decide whether the evidence `SUPPORTS`, `CONTRADICTS`, or is `INCONCLUSIVE`.
     * INCONCLUSIVE downgrades to `NOT_FOUND`. SUPPORTED and CONTRADICTED update the claim verdict and explanation.
     * Tie-breaker rules in the LLM prompt: only prefer SUPPORTED on vague/unspecified timeframes when the evidence year matches/is unspecified or is within ~1 year; otherwise lean INCONCLUSIVE. Mark CONTRADICTED only on clear numeric or timeframe conflicts; if numbers match and timeframe is acceptable, lean SUPPORTED.
   - If `s_max` is below the threshold we keep the claim as `NOT_FOUND`.
   - Each evidence row (including non-top hits) is stored with snippet, similarity score, haystack score, rerank score, classification metadata, and parent context (page/title/text/summary).
3. **Persistence** – Claims and evidence go into SQLite. Per-report FAISS indexes are built for (a) claims (`CLAIM_VECTOR_PATH/report_id`) using `Claim: … / Verdict: … / Explanation: …` strings, and (b) supporting snippets (`SOURCE_VECTOR_PATH/report_id`).
4. **Summary** – Counts `supported`, `contradicted`, `not_found` are written into the report metadata (`accuracy_summary`, etc.). The HTTP APIs expose this via `/api/reports/*`.

Recommendations (OpenAlex)
--------------------------
- Keyword/topic derivation: build a corpus from report title/summary, all claim texts, and available source summaries; stem and score frequent tokens; top terms become the search query and topic filter. No static domain guardrails are used.
- Retrieval: call OpenAlex `/works` with the derived query/terms, deduplicate against existing sources.
- On-topic check: keep only candidates whose title/abstract contains at least one derived term.
- Re-rank: embed the report/claim context and candidate titles/abstracts, compute cosine similarity, drop low-relevance candidates, and sort by relevance with minor boosts for recency/credibility.


Key configuration
-----------------
- `RETRIEVAL_SUPPORT_THRESHOLD` – similarity cutoff for SUPPORTED verdicts (fraction).
- `RERANK_MODEL` / `OPENAI_API_KEY` – enables GPT reranking; code falls back automatically if absent.
- `CLAIM_VECTOR_PATH`, `SOURCE_VECTOR_PATH`, `FAISS_INDEX_DIR` – directories for persisted FAISS indexes.
- `PDF_OCR_*` env vars – control when OCR is triggered.


Operational notes
-----------------
- Re-indexing sources resets the FAISS “sources” store (`VectorStore("sources")`).
- Reranker prompts are deterministic (temperature 0.1) but you can disable reranking via environment by clearing `RERANK_MODEL` or API keys.
- Parent sections cached in `_section_cache` ensure that chat explanations can reference “Page N” without a second pass over the PDF.
